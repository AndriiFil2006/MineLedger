# Connection modes: automatic, online required, offline practice

MineLedger decides at run time whether to show curriculum from the FastAPI backend (`../backend/`) or the
curriculum bundled in the mod. Students choose in **MineLedger → Settings**; nobody has to edit a file.

- **Online is view-only.** Backend content can be browsed (course → unit → assignment → concepts →
  question preview). It is not graded and earns nothing. Nothing is ever sent to the backend except
  read-only `GET` requests.
- **Offline practice is the existing local workflow**, unchanged: local grading, mastery, XP, Recharge and
  the Journal Entries lab, saved in `mineledger/progress/<uuid>.json`. Its XP is labeled **local XP**. It is
  practice, not official coursework, and it is never uploaded or synchronized.

## The three preferences

| Setting (file value) | Behavior |
| --- | --- |
| Automatic (`auto`, default) | Checks the server when MineLedger opens. Usable → online. Otherwise → offline practice, with the reason shown and a Retry Connection button |
| Online Required (`backend`) | Uses the server only. If it cannot be used, shows the error with Retry Connection. Offline content appears only if the student presses Switch to Offline Practice |
| Offline Practice (`offline`) | Never contacts the server; no HTTP client is even created |

The choice applies immediately and is saved to `<game directory>/mineledger/config.json` (development
client: `run/mineledger/config.json`):

```json
{
  "config_version": 2,
  "mode": "auto",
  "backend_url": "http://127.0.0.1:8000",
  "connect_timeout_ms": 3000,
  "request_timeout_ms": 5000
}
```

`backend_url` and the timeouts (100–60000 ms) are still edited in the file and read at startup. The file
holds no secrets; URLs with credentials are rejected.

**Existing files.** A file with an explicit `"mode": "offline"` or `"backend"` keeps that behavior. A file
without `mode` now means automatic. The file the previous version generated by itself on first launch
(explicit offline, all defaults, never edited) is read as automatic, because nobody chose it; any edit makes
it count as a choice. Files saved by this version carry `config_version`, so a saved Offline Practice choice
is never mistaken for that old template. An unreadable file means defaults plus a warning in Settings;
saving a choice replaces it and keeps a copy as `config.invalid.json`. Saves go through a temporary file
and an atomic move.

## Connection states (`ConnectionManager`)

| State | Title bar | Content shown |
| --- | --- | --- |
| `CHECKING` | Checking connection... | Nothing yet (first check), or whatever was already shown (recheck) |
| `ONLINE` | Online | Backend, view-only |
| `CONNECTION_LOST` | Connection lost | Backend content already loaded stays on screen |
| `OFFLINE_PRACTICE` | Offline practice | Bundled curriculum; reason is `CHOSEN`, `FALLBACK` or `SWITCHED` |
| `UNAVAILABLE` | Server unavailable | Nothing (Online Required and the check failed) |

**A check** is `GET /health` → `GET /api/v1/meta` → `GET /api/v1/courses`. The server is usable only if it
is healthy, reports `api_version` 1, holds curriculum only in schema version 1, and returns the number of
courses it claims (at least one). Failures are classified as `UNREACHABLE`, `TIMEOUT`, `HTTP_STATUS`,
`MALFORMED_RESPONSE` or `INCOMPATIBLE` (wrong version, no courses, or a server too old to have `/meta`).

**When checks happen.** When MineLedger is opened from the MineOS desktop, unless a check finished less
than 15 seconds ago, one is already running, the preference is offline, or the student switched to offline
practice. Also on Retry Connection and when the preference changes. There is no background polling.

**Transitions that need the student.**

- A request that fails while online gives `CONNECTION_LOST`, never an automatic switch: the page already
  open stays, with Retry Connection and Switch to Offline Practice. A failed retry stays in that state.
- Switch to Offline Practice is a session choice. Reopening the app does not undo it; Retry Connection does.
- Automatic mode falls back by itself only when deciding fresh: on opening the app or after a retry from
  offline practice.

**Active local questions are isolated.** `ConceptAssignmentScreen` and `JournalEntryScreen` never consult the
connection. A status change while a student is answering does not touch the question, the selected option
or the attempt; it is visible only after returning to the MineLedger home screen. An attempt therefore
always finishes against the local question set it started with.

**Threading.** Everything runs on the client thread except HTTP and JSON parsing (`MineLedger-Backend-*`
threads). Results are passed to `Minecraft::execute`. Each check and each page load carries a ticket; a
result whose ticket is stale (newer request, Back, preference change, switch to offline, screen closed) is
dropped without changing state.

## Code map (`src/main/java/com/mineledger/backend/`, no Minecraft classes)

| Class | Role |
| --- | --- |
| `BackendConfig` | Parse, validate, migrate and save `config.json` |
| `ConnectionManager` | Preference + check results → state and allowed content; retry, switch, listeners |
| `CurriculumApi` / `BackendClient` | Eight asynchronous read operations over `java.net.http` (two daemon threads, timeouts plus an overall deadline, no redirects) |
| `BackendJson`, `RemoteCurriculum` | Strict JSON → typed view-only records (no answer keys can be carried) |
| `BackendException` | Classified, display-safe failures |
| `RemoteCurriculumBrowser` | Navigation over backend content, consistency checks, stale-response protection, failure reporting |

Client: `client/BackendRuntime` (builds the manager, saves preferences), `MineLedgerScreen` (status,
Settings tab, connection actions, chooses local or remote view), `screen/RemoteCourseBrowser` (draws
backend content).

## Tests

`src/test/java/com/mineledger/backend/`: `ConnectionManagerTest` (mode selection, fallback, timeout,
malformed and incompatible servers, outage with a screen open, stale results, preference changes, reconnection,
progress preservation, no duplicate XP, Recharge, read-only traffic), `BackendConfigTest` (modes, migration,
saving), plus the HTTP client, JSON and browser tests. They use real response bodies from
`../shared/fixtures/api_responses/`, which `backend/tests/test_api_contract.py` holds the API to.

## Manual verification (Windows PowerShell)

Set `JAVA_HOME` once if you have not (`setx JAVA_HOME "C:\Program Files\Java\jdk-25.0.5.0.3"`, new window).

```powershell
# Window 1: server (Docker Desktop running). Leave open.
cd D:\work\minecraft_mods\accounting\backend
docker compose up -d --wait
.\.venv\Scripts\alembic upgrade head
.\.venv\Scripts\mineledger import-curriculum
.\.venv\Scripts\uvicorn mineledger_api.main:app --port 8000

# Window 2: game
cd D:\work\minecraft_mods\accounting\minecraft-mod
./gradlew.bat runClient
```

In a world: right-click the computer → MineOS → MineLedger.

1. **Choose Automatic.** Settings → Automatic. Title bar: `Online`. Courses shows "Online courses
   (view-only)"; open Accounting 101 → Unit 2 → Assignment 2.1 → Preview Questions.
2. **Outage while browsing.** Stay on a question. Press Ctrl+C in Window 1. Click Back to Assignment, Back,
   then the assignment again. Expect `Connection lost`, "This page could not be loaded", Retry Connection
   and Switch to Offline Practice; Back returns to the unit page that was already loaded. The game must not
   freeze. Retry Connection: still lost.
3. **Reconnection.** Start uvicorn again, press Retry Connection: `Online`, and browsing works again (a
   page that failed is reloaded automatically if it is still on screen).
4. **Fallback.** Stop uvicorn. Go Back to Desktop, wait 15 seconds, open MineLedger: `Offline practice`
   with "The MineLedger server is not available". Answer a question in Assignment 2.1; XP is shown as
   local XP. Start uvicorn, press Retry Connection: `Online`.
5. **Mid-question.** Stop uvicorn, reopen MineLedger after 15 seconds (offline practice), start an
   assignment and select an answer. Start uvicorn. Nothing changes on the question screen; finish it normally.
6. **Online Required.** Settings → Online Required with uvicorn stopped: `Server unavailable`, an error,
   no courses. Switch to Offline Practice shows local content; Settings still says Online Required.
7. **Offline Practice.** Settings → Offline Practice: Window 1 shows no requests at all, even after
   reopening. Recharge Practice on a completed assignment awards no XP.
8. **Persistence.** Close the game and start it again: the last chosen setting is still selected, and
   Progress shows the same local XP as before (no XP was gained by switching modes).

## Not in this milestone

- No grading, XP or progress on the backend; no authentication; no synchronization. Local progress is never
  converted into official progress.
- **For future authoritative submissions:** a timeout must never be read as "not processed". Each submission
  will need a client-generated idempotency key, stored and deduplicated by the backend, so a retry after a
  lost response returns the original result instead of grading or rewarding twice. The client must keep the
  pending key with the attempt until the server confirms it, and must not offer offline grading for an
  attempt whose submission is in doubt.
- The server URL is not editable in the Settings tab.
- Backend content has no revision identifier yet; content consistency is checked per page load, and `/meta`
  reports only versions and a course count.
- Rechecks happen on opening the app and on request, not continuously, so the status can be out of date
  until the next action.
- `java.net.http` and the screens were exercised in the development client only.
